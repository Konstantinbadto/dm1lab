# Лабораторная работа № 2
## Разработка серверных приложений: проектирование REST API и спецификации OpenAPI 3.0

**Тема проекта:** «Трекер личных коллекций (книги, винил, настольные игры)»

## 1. Цель работы

Цель лабораторной работы — спроектировать REST API для клиент-серверного взаимодействия в системе учёта личных коллекций, определить HTTP-методы и коды ответов, а также описать контракт API в формате OpenAPI 3.0.3.

## 2. Описание предметной области

«Трекер личных коллекций» позволяет коллекционеру хранить сведения о книгах, виниловых пластинках и настольных играх, группировать предметы по коллекциям, задавать пользовательские атрибуты и отслеживать состояние предметов.

Для предметов предусмотрены статусы:

- `IN_STOCK` — в наличии;
- `LENT_TO_FRIEND` — отдан другу;
- `WANTED` — в желаемом.

Основные роли системы:

- **Коллекционер** — регистрируется, входит в систему, управляет своим профилем, коллекциями, предметами и пользовательскими атрибутами.
- **Гость профиля** — просматривает публичный профиль и открытые коллекции, но не может изменять чужие данные.

## 3. Проектирование REST API

API использует базовый адрес `http://localhost:8080/api/v1`. Имена ресурсов представлены существительными во множественном числе. Идентификаторы передаются в path-параметрах, фильтры — в query-параметрах, а данные создания и изменения — в теле JSON-запроса.

### 3.2. Используемые HTTP-статусы

| Код | Значение | Применение |
|---|---|---|
| `200 OK` | Запрос выполнен успешно | Получение и изменение ресурса |
| `201 Created` | Ресурс создан | Регистрация, создание коллекции или предмета |
| `204 No Content` | Успех без тела ответа | Выход или удаление ресурса |
| `400 Bad Request` | Некорректные данные | Ошибка проверки тела запроса или параметров |
| `401 Unauthorized` | Нет действительной аутентификации | Отсутствует или недействителен токен |
| `403 Forbidden` | Недостаточно прав | Попытка изменить чужой ресурс |
| `404 Not Found` | Ресурс не найден | Коллекция, предмет или профиль отсутствует |
| `409 Conflict` | Конфликт данных | Например, занятый `username` или `email` |
| `500 Internal Server Error` | Внутренняя ошибка сервера | Необработанная серверная ошибка |

## 4. Спецификация OpenAPI

Контракт API находится в файле [`openapi.yaml`](openapi.yaml). Используется версия OpenAPI `3.0.3`.

В спецификации описаны:

- регистрация, вход и выход;
- просмотр и изменение профиля;
- CRUD-операции над коллекциями;
- CRUD-операции над предметами;
- фильтрация предметов по коллекции, типу и статусу;
- добавление и удаление пользовательских атрибутов;
- Bearer-аутентификация;
- схемы запросов, ответов и ошибок.

### 4.1. Основные схемы данных

| Схема | Назначение |
|---|---|
| `RegisterRequest` | Данные регистрации |
| `LoginRequest` | Учётные данные для входа |
| `AuthResponse` | Токен и сведения о пользователе |
| `ProfileResponse` | Публичные данные профиля |
| `CreateCollectionRequest` | Данные новой коллекции |
| `CollectionResponse` | Ответ с данными коллекции |
| `CreateItemRequest` | Данные нового предмета |
| `UpdateItemRequest` | Поля для частичного изменения предмета |
| `ItemResponse` | Ответ с данными предмета и атрибутами |
| `ItemAttributeInput` | Входные данные пользовательского атрибута |
| `ItemAttributeResponse` | Представление пользовательского атрибута |
| `ErrorResponse` | Единый формат сообщения об ошибке |

Повторно используемые схемы подключаются с помощью `$ref`, например `#/components/schemas/ItemResponse`. Это уменьшает дублирование и поддерживает единый формат данных.

## 6. Ответы на контрольные вопросы

### Вопрос 1. В чём разница между передачей параметров через Query, Path и Request Body?

**Query-параметры** передаются после `?` в URL и используются для фильтрации, поиска, сортировки и пагинации. Пример: `GET /api/v1/items?status=WANTED&limit=10`.

**Path-параметры** входят в путь URL и идентифицируют конкретный ресурс. Пример: `GET /api/v1/items/{itemId}`.

**Request Body** — тело HTTP-запроса, обычно содержащее JSON с данными для создания или изменения ресурса. Например, `POST /api/v1/items` получает в теле название, тип, статус и идентификатор коллекции.

### Вопрос 2. Что такое идемпотентность HTTP-методов? Почему GET, PUT и DELETE считают идемпотентными, а POST — нет?

Идемпотентность означает, что повторение одинакового запроса приводит к тому же состоянию ресурса на сервере, что и однократный запрос.

- `GET` предназначен для чтения и не должен менять состояние сервера.
- `PUT` устанавливает заданное представление ресурса; повторение того же запроса не должно приводить к дополнительным изменениям.
- `DELETE` удаляет ресурс; после первого удаления повторный запрос не должен вызывать дополнительных изменений состояния. При этом код ответа может отличаться.
- `POST` часто создаёт новый ресурс, поэтому повторный запрос может создать ещё один ресурс и не является идемпотентным по умолчанию.

### Вопрос 3. Когда сервер должен возвращать 401 Unauthorized, а когда 403 Forbidden?

`401 Unauthorized` возвращается, когда пользователь не аутентифицирован: токен отсутствует, недействителен или истёк.

`403 Forbidden` возвращается, когда пользователь успешно аутентифицирован, но не имеет права выполнять действие. Например, коллекционер пытается изменить предмет другого пользователя.

### Вопрос 4. Для чего нужны components/schemas и ключевое слово $ref?

`components/schemas` содержит описания структур данных, которые используются в запросах и ответах API. Например, `CreateItemRequest`, `ItemResponse` и `ErrorResponse`.

`$ref` ссылается на ранее определённую схему. Это позволяет повторно использовать описание, не копировать его во все эндпоинты и поддерживать единообразие контракта.

Пример:

```yaml
schema:
  $ref: '#/components/schemas/ItemResponse'
```

### Вопрос 5. В чём разница между PUT и PATCH при обновлении ресурсов?

`PUT` предназначен для полной замены представления ресурса согласно контракту API. `PATCH` предназначен для частичного изменения: клиент передаёт только поля, которые требуется изменить.

В проекте для смены статуса предмета применяется `PATCH /api/v1/items/{itemId}` с телом:

```json
{
  "status": "LENT_TO_FRIEND"
}
```

Остальные поля предмета при таком частичном обновлении сохраняются.
