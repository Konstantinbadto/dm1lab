# Отчёт по лабораторной работе № 3

**Дисциплина:** Разработка серверных приложений  
**Тема:** Создание базового каркаса приложения, архитектура Clean / Layered Architecture и настройка окружения  
**Продолжительность:** 2 академических часа (1 занятие)

## 1. Цель работы
Изучить принципы многослойной архитектуры, инициализировать базовый проект серверного приложения, организовать структуру каталогов, настроить загрузку конфигурации из переменных окружения и реализовать health-check endpoint.

## 2. Используемые технологии
Node.js, TypeScript, Express, dotenv, npm.

## 3. Выполнение работы

### 3.1. Инициализация проекта
Создан проект `Collection Tracker API` на Node.js + TypeScript. Добавлены `package.json` и `tsconfig.json`. В `.gitignore` исключены зависимости, сборка, логи, IDE-файлы и `.env`. Шаблон `.env.example` разрешён для коммита.

### 3.2. Структура каталогов
- `config` — чтение и валидация конфигурации;
- `routes` — маршруты HTTP API;
- `controllers` — обработчики запросов и ответы;
- `services` — бизнес-логика;
- `repositories` — слой доступа к данным, подготовленный к дальнейшему подключению СУБД;
- `app.ts` — сборка Express-приложения;
- `server.ts` — запуск HTTP-сервера.

### 3.3. Конфигурация
Создан `.env.example`:
```dotenv
APP_NAME="Collection Tracker API"
APP_VERSION=1.0.0
APP_ENV=development
HTTP_PORT=8080
```
`src/config/env.ts` загружает `.env` через `dotenv`. Значение порта проверяется; недопустимое значение вызывает ошибку. Файл `.env` не должен попадать в Git.

### 3.4. Health-check
Реализован `GET /api/v1/health`. Контроллер вызывает `HealthService`, который возвращает статус, имя сервиса, версию, окружение и время работы процесса.

Пример ответа:
```json
{
  "status": "pass",
  "app_name": "Collection Tracker API",
  "version": "1.0.0",
  "environment": "development",
  "uptime_seconds": 3
}
```
Ожидается `200 OK` и `Content-Type: application/json`.

### 3.5. Проверка проекта
```bash
npm install
cp .env.example .env
npm run typecheck
npm run build
npm run dev
curl http://localhost:8080/api/v1/health
```
В Windows PowerShell: `Copy-Item .env.example .env`. После запуска endpoint также можно открыть в браузере или проверить через Postman.

### 3.6. Фиксация изменений
```bash
git add .
git commit -m "feat: init project structure, config loader and health endpoint for Lab 3"
git push origin main
```
Команды выполняются из корня репозитория. Перед коммитом следует проверить, что `.env` не отслеживается Git.

## 4. Результат
Создан базовый каркас серверного приложения для трекера личных коллекций. Код разделён на слои, параметры читаются из окружения, а endpoint `GET /api/v1/health` возвращает базовую информацию о состоянии процесса. Спецификация OpenAPI из ЛР2 сохранена.

## 5. Контрольные вопросы

### 1. Почему слой бизнес-логики не должен знать о деталях HTTP-запросов?
Бизнес-логика должна описывать правила предметной области, а не транспорт. Если сервис зависит от Express, JSON-тела или HTTP-заголовков, его сложнее повторно использовать и тестировать. Независимый сервис можно вызывать из HTTP API, CLI или фоновой задачи. Контроллер преобразует HTTP-запрос в параметры сервиса и преобразует результат в HTTP-ответ.

### 2. В чём опасности хранения секретов непосредственно в исходном коде?
Секреты могут попасть в Git-историю, логи, сборки и копии проекта. При утечке злоумышленник может получить доступ к БД или стороннему API. Удаление секрета из последнего коммита не обязательно удаляет его из истории. Секреты нужно хранить в переменных окружения или хранилище секретов, исключать `.env` из Git, ограничивать доступ и менять скомпрометированные ключи.

### 3. Зачем нужен `.env.example`, если `.env` находится в `.gitignore`?
`.env.example` документирует нужные параметры и их имена, помогая другому разработчику настроить локальное окружение. По нему создают собственный `.env`, не передавая реальные пароли и токены. В шаблоне должны быть только безопасные демонстрационные значения.

### 4. Для чего используется Health Check (`/health`)?
Health Check позволяет мониторингу, балансировщику нагрузки и разработчику проверить, отвечает ли приложение. Это помогает обнаруживать остановившиеся или недоступные процессы. Простой `/health` обычно проверяет сам процесс, а отдельный readiness-check может дополнительно проверять зависимости, например базу данных. В этой работе проверяется доступность процесса приложения.

### 5. Что такое инверсия зависимостей и как она помогает связывать API, сервисы и репозитории?
Dependency Inversion Principle (DIP) означает, что высокоуровневые модули не должны зависеть от низкоуровневых деталей: оба должны зависеть от абстракций. Например, сервис зависит от интерфейса `ItemRepository`, а не от конкретного класса с SQL-запросами PostgreSQL. Реализация интерфейса подключается при сборке приложения. Это позволяет заменить БД или использовать тестовую реализацию без изменения бизнес-логики. API вызывает сервис, сервис работает с абстракциями репозиториев, а детали инфраструктуры остаются снаружи.

Настроена загрузка и валидация переменных окружения, подготовлены `.gitignore` и `.env.example`, реализован `GET /api/v1/health`.
