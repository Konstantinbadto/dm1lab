# Архитектура проекта «Трекер личных коллекций»

## 1. Краткое описание проекта

**Трекер личных коллекций** — веб-приложение для хранения, управления и публичного просмотра личных коллекций книг, виниловых пластинок и настольных игр.

Коллекционер может создавать несколько коллекций, добавлять в них предметы, указывать общие характеристики и задавать кастомные атрибуты, зависящие от типа предмета. Для каждого предмета предусмотрен статус: **«В наличии»**, **«Отдал другу»** или **«В желаемом»**.

Гость профиля может просматривать публичный профиль коллекционера и его опубликованные коллекции, но не имеет права изменять данные.

---

## 2. Цели системы

1. Предоставить единое место для хранения информации о личных коллекциях.
2. Поддерживать разные типы коллекционных предметов.
3. Позволить использовать кастомные атрибуты без изменения основной структуры таблицы предметов.
4. Обеспечить изменение текущего статуса предмета.
5. Предоставить публичный просмотр коллекции.
6. Обеспечить поиск и фильтрацию предметов.

---

## 3. Ролевая модель

| Роль | Описание |
|---|---|
| **Коллекционер** | Владелец и редактор личных коллекций |
| **Гость профиля** | Просматривает публичный профиль и опубликованные коллекции |

### 3.1. Возможности коллекционера

- регистрация;
- вход в систему;
- редактирование профиля;
- создание и удаление коллекций;
- добавление, изменение и удаление предметов;
- изменение статуса предмета;
- добавление и изменение кастомных атрибутов;
- поиск и фильтрация предметов;
- настройка публичности профиля.

### 3.2. Возможности гостя

- открытие публичного профиля;
- просмотр публичных коллекций;
- просмотр информации о предметах;
- поиск и фильтрация доступных публичных предметов.

Гость не может изменять коллекции, предметы или профиль другого пользователя.

## 4. Use Cases

### UC-01 — Регистрация

**Актор:** Коллекционер.

1. Пользователь открывает страницу регистрации.
2. Вводит имя пользователя, email и пароль.
3. Система проверяет уникальность email и имени пользователя.
4. Система создаёт пользователя.
5. Пользователь получает доступ к своему профилю.

### UC-02 — Вход в систему

**Актор:** Коллекционер.

1. Пользователь вводит email и пароль.
2. Backend проверяет учётные данные.
3. При успешной проверке создаётся авторизованная сессия.
4. Пользователь получает доступ к управлению коллекциями.

### UC-03 — Создание коллекции

**Актор:** Коллекционер.

1. Пользователь открывает раздел коллекций.
2. Нажимает «Создать коллекцию».
3. Указывает название и описание.
4. Система создаёт коллекцию и связывает её с пользователем.

### UC-04 — Добавление предмета

**Актор:** Коллекционер.

1. Пользователь открывает нужную коллекцию.
2. Нажимает «Добавить предмет».
3. Выбирает тип: книга, винил или настольная игра.
4. Вводит название и основные характеристики.
5. Устанавливает статус.
6. При необходимости добавляет кастомные атрибуты.
7. Система сохраняет предмет.

### UC-05 — Изменение статуса предмета

**Актор:** Коллекционер.

Пользователь может изменить статус предмета, например:

`В желаемом → В наличии`

или

`В наличии → Отдал другу`.

### UC-06 — Добавление кастомного атрибута

**Актор:** Коллекционер.

1. Пользователь открывает предмет.
2. Выбирает добавление атрибута.
3. Указывает название, тип и значение атрибута.
4. Система сохраняет значение.

Примеры:

- книга: ISBN, количество страниц, язык, издательство;
- винил: лейбл, год издания, страна выпуска, скорость вращения;
- настольная игра: количество игроков, возраст, время партии, язык.

### UC-07 — Просмотр публичного профиля

**Актор:** Гость профиля.

1. Гость открывает ссылку на профиль.
2. Система проверяет, что профиль является публичным.
3. Отображаются опубликованные коллекции.
4. Гость может открыть отдельный предмет.

### UC-08 — Поиск предметов

**Актор:** Коллекционер / Гость.

Система позволяет искать предметы по названию, типу и автору/создателю, а также фильтровать их по статусу.

### UC-09 — Удаление предмета

**Актор:** Коллекционер.

1. Пользователь открывает свой предмет.
2. Нажимает «Удалить».
3. Подтверждает действие.
4. Система удаляет предмет и связанные значения его кастомных атрибутов.

## 6. Описание таблиц

### 6.1. User

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUID | PK |
| `username` | VARCHAR(50) | NOT NULL, UNIQUE |
| `email` | VARCHAR(255) | NOT NULL, UNIQUE |
| `password_hash` | VARCHAR(255) | NOT NULL |
| `created_at` | TIMESTAMP | NOT NULL |

### 6.2. Profile

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUID | PK |
| `user_id` | UUID | FK → User.id, UNIQUE, NOT NULL |
| `display_name` | VARCHAR(100) | NOT NULL |
| `description` | TEXT | NULL |
| `is_public` | BOOLEAN | NOT NULL |
| `created_at` | TIMESTAMP | NOT NULL |

Связь: **User 1 — 1 Profile**.

### 6.3. Collection

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUID | PK |
| `user_id` | UUID | FK → User.id, NOT NULL |
| `name` | VARCHAR(100) | NOT NULL |
| `description` | TEXT | NULL |
| `created_at` | TIMESTAMP | NOT NULL |

Связь: **User 1 — N Collection**.

### 6.4. ItemType

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | SMALLINT | PK |
| `name` | VARCHAR(50) | NOT NULL, UNIQUE |

Примеры: `BOOK`, `VINYL`, `BOARD_GAME`.

### 6.5. ItemStatus

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | SMALLINT | PK |
| `name` | VARCHAR(50) | NOT NULL, UNIQUE |

Примеры: `IN_STOCK`, `LENT_TO_FRIEND`, `WANTED`.

### 6.6. Item

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUID | PK |
| `collection_id` | UUID | FK → Collection.id, NOT NULL |
| `type_id` | SMALLINT | FK → ItemType.id, NOT NULL |
| `status_id` | SMALLINT | FK → ItemStatus.id, NOT NULL |
| `title` | VARCHAR(255) | NOT NULL |
| `creator` | VARCHAR(255) | NULL |
| `description` | TEXT | NULL |
| `created_at` | TIMESTAMP | NOT NULL |
| `updated_at` | TIMESTAMP | NOT NULL |

Связи: **Collection 1 — N Item**, **ItemType 1 — N Item**, **ItemStatus 1 — N Item**.

### 6.7. AttributeDefinition

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUID | PK |
| `item_type_id` | SMALLINT | FK → ItemType.id, NOT NULL |
| `name` | VARCHAR(100) | NOT NULL |
| `data_type` | VARCHAR(20) | NOT NULL |
| `is_required` | BOOLEAN | NOT NULL |

Таблица определяет, какие кастомные характеристики доступны для конкретного типа предмета.

### 6.8. ItemAttributeValue

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUID | PK |
| `item_id` | UUID | FK → Item.id, NOT NULL |
| `attribute_definition_id` | UUID | FK → AttributeDefinition.id, NOT NULL |
| `value` | TEXT | NOT NULL |

Ограничение: `UNIQUE(item_id, attribute_definition_id)`.

## 8. Нормализация до 3NF

База данных спроектирована в соответствии с требованиями третьей нормальной формы (3NF).

### Первая нормальная форма (1NF)

Все поля содержат атомарные значения. Множественные значения не хранятся в одном поле. Например, тип предмета вынесен в отдельную таблицу `ItemType`.

### Вторая нормальная форма (2NF)

Каждый неключевой атрибут зависит от полного первичного ключа своей сущности. Данные предмета хранятся в `Item`, а данные коллекции — в `Collection`.

### Третья нормальная форма (3NF)

Транзитивные зависимости устранены. Название типа и название статуса не дублируются в таблице `Item`, а хранятся в справочниках `ItemType` и `ItemStatus` и связываются через внешние ключи.

Кастомные атрибуты также вынесены в `AttributeDefinition` и `ItemAttributeValue`, поэтому структура `Item` не изменяется при добавлении новых характеристик.

## 9. Индексы

Для внешних ключей и часто используемых полей предусматриваются индексы:

```sql
CREATE UNIQUE INDEX idx_user_email

CREATE UNIQUE INDEX idx_user_username
ON users(username);

CREATE INDEX idx_collection_user
ON collections(user_id);

CREATE INDEX idx_item_collection
ON items(collection_id);

CREATE INDEX idx_item_type
ON items(type_id);

CREATE INDEX idx_item_status
ON items(status_id);

CREATE INDEX idx_item_title
ON items(title);

CREATE INDEX idx_attribute_value_item
ON item_attribute_values(item_id);

CREATE INDEX idx_attribute_definition_type
ON attribute_definitions(item_type_id);

CREATE UNIQUE INDEX idx_item_attribute_unique
ON item_attribute_values(item_id, attribute_definition_id);
```

## 10. C4 Container Diagram

Диаграмма разработана на уровне **C4 Container (Level 2)**. Она показывает основные контейнеры приложения и взаимодействие между ними.

![C4 Container Diagram](docs/diagrams/c4-container.png)

### 10.1. Web Client

**Технологии:** React / TypeScript.

Отвечает за:

- отображение пользовательского интерфейса;
- формы регистрации и авторизации;
- отображение коллекций и предметов;
- поиск и фильтрацию;
- отправку HTTP-запросов к Backend Service.

### 10.2. Backend Service

**Технологии:** Node.js / REST API.

Отвечает за:

- аутентификацию и авторизацию;
- проверку прав доступа;
- управление коллекциями;
- управление предметами;
- управление статусами;
- управление кастомными атрибутами;
- валидацию данных;
- взаимодействие с PostgreSQL.

### 10.3. PostgreSQL

Реляционная база данных для хранения:

- пользователей;
- профилей;
- коллекций;
- предметов;
- типов предметов;
- статусов;
- определений кастомных атрибутов;
- значений кастомных атрибутов.

Redis/Queue в минимальной архитектуре не используется, поскольку для основных сценариев приложения отдельная очередь сообщений или кэширование не являются обязательными.

## 11. Взаимодействие контейнеров

### Коллекционер → Web Client

Коллекционер работает с системой через веб-браузер.

### Гость → Web Client

Гость открывает публичный профиль через веб-интерфейс.

### Web Client → Backend Service

Взаимодействие выполняется через HTTP/REST с передачей данных в JSON.

Примеры:

```text
POST   /api/auth/register
POST   /api/auth/login
POST   /api/auth/logout

GET    /api/profiles/{username}
PATCH  /api/profile

GET    /api/collections
POST   /api/collections
GET    /api/collections/{id}
PATCH  /api/collections/{id}
DELETE /api/collections/{id}

GET    /api/items
POST   /api/items
GET    /api/items/{id}
PATCH  /api/items/{id}
DELETE /api/items/{id}
```

### Backend Service → PostgreSQL

Backend Service выполняет SQL-запросы к PostgreSQL для чтения и изменения данных.

## 13. Безопасность

Backend Service должен обеспечивать:

- хранение паролей только в виде криптографических хэшей;
- аутентификацию и авторизацию;
- проверку владельца коллекции перед изменением данных;
- валидацию входных данных;
- защиту от SQL-инъекций через параметризованные запросы или ORM;
- проверку публичности профиля перед выдачей данных гостю;
- проверку допустимых типов и статусов предметов.

Особенно важно проверять права пользователя на сервере, а не только скрывать элементы интерфейса:

```text
PATCH /api/items/{id}
        ↓
Проверка авторизации
        ↓
Проверка принадлежности Item пользователю
        ↓
Валидация данных
        ↓
Изменение Item
```
